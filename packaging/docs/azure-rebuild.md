# Can the contract express today's Azure?

`azure-parity.md` compared production to the standard-production **example** and listed the
differences. This asks the question underneath it: is there *any* document in this contract's
vocabulary that describes what production actually runs? Until the answer is yes, every parity
number is a comparison against a target the deployment could not have expressed, and PRD §21
phase 3's *"rebuild the current Azure deployment using the common contract"* has nothing to
rebuild from.

The answer is **almost**, and the two things that were missing are worth more than the answer.

Everything below the markers is generated from `deploy/public/*.sh`. Everything above is
authored, because what a gap in the contract means is a judgement and a generator should not make
one.

## The two things the contract could not say

**A per-replica connection pool.** `rightsize-production.sh` pins `ACP_DB_MAX_CONN=2` on all
three worker tiers (PR #1370), which is what holds the fleet inside the Postgres server's
measured 150-connection ceiling. The contract derived each replica's pool from
`ACP_WORKERS + headroom` and had no way to record an override — so the honest document, with
today's real replica ranges and the real server, computed **384** worst-case connections and read
as 2.5× oversubscribed. The deployment it described sits at **82** and has never exhausted its
pool.

The contract was not *wrong* about production. It was *unable to describe it*, which is the
quieter failure: `acpctl plan` would have refused a configuration that is demonstrably safe, and a
plan that refuses safe configurations teaches an operator to stop reading plans. `tier.
connectionPool` closes it, and `inventory.pool_per_replica` mirrors `api/store.py`'s override
semantics exactly — the override **replaces** the formula rather than capping it, because
`db_max_conn` returns `max(2, explicit)` without consulting `ACP_WORKERS` at all. A model that
took the smaller of the two would agree with production by luck today and disagree the moment
somebody pinned a pool *larger* than the formula, which is the direction an operator raising a
limit would move.

**An access path with no credential.** The contract required an `object-storage` secret reference
for any non-embedded object storage. Production holds no storage credential: `deploy.sh` grants
the worker's managed identity Storage Blob Data Contributor and reaches Blob Storage that way.
There was no way to say so, and the only route to a passing validation was to declare a secret
that does not exist.

That is the rule failing in the worst possible direction — pushing an operator to *create* a
credential in order to satisfy a security check. `secrets.workloadIdentity` closes it, and the
requirement is unchanged: the installation must be able to reach the service, and the platform's
own identity satisfies that better than a stored secret does. This is not an Azure quirk;
workload identity is the recommended pattern on AKS, EKS and GKE alike, so the gap would have
reappeared on every cloud in phase 4.

## The two errors that remain are findings, not defects in the derivation

**Production runs one API replica; the standard profile requires two.** The validator now says
what `azure-parity.md` could only assert. Same finding, from the contract's own rules rather than
from a reading of them.

**Backup retention is not derivable.** `deploy/public/` does not provision the Postgres server —
it is created outside these scripts — so the document leaves retention unstated rather than
guessing at Azure's default, and the contract fail-closes an absent retention to "no backups".
The failure is the useful part: the Azure adapter has to own server provisioning before any
document can honestly claim a retention period.

Neither is fixed here. Fixing the first is a production change and the owner's call; fixing the
second is phase 3's remaining work.

## One field describes the target rather than today, and only one

`secrets.provider` says `azure-key-vault`. Production keeps its secrets in the **container app's
own** store (`secretref:` in `deploy.sh`), which is not one of the six backends the contract
offers. It is recorded as the adapter a rebuild would use, because `presets.py` already states
that ACA is the legacy path the contract does not target and no rebuild onto AKS could carry an
ACA secret store across. Every other field in the generated document is what the scripts
configure.

## What the contract could not express

Fields this document states differently from the deployment, or leaves unstated, with why.

- **`data.postgres.backupRetentionDays`** — `deploy/public/` does not provision the Postgres server — it is created outside these scripts — so backup retention is not derivable from them. Deliberately left unstated rather than guessed at Azure's default, which makes the document fail validation. That failure is the finding: the Azure adapter has to own server provisioning before this document can honestly claim a retention period.
- **`metadata.region`** — deploy.sh takes the region from its environment, so the scripts do not record one.
- **`secrets.provider`** — Production keeps its secrets in the CONTAINER APP's own secret store (`secretref:` in deploy.sh), which is not one of the six backends the contract offers. Recorded here as `azure-key-vault` because that is the adapter a rebuild would use — presets.py already says ACA is the legacy path the contract does not target, and no rebuild on AKS could carry the ACA secret store across anyway. So this one field describes the TARGET, not today, and it is the only field in this document that does.

## What this cannot see

Everything above is what the SCRIPTS configure. The same three blind spots as `azure-parity.md`: discovery's scale rule (applied outside this repository), `ACP_WORKER_ROLE` on assess and remediate (set outside these scripts), and any change made by hand in the portal.

The release is recorded as `2026.9` because `deploy/public/` deploys whatever image the pipeline built and states no version — that one value is the CLI's default, not a fact read from the scripts.
