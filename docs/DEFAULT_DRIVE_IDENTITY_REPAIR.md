# Default-drive source identity recovery

Discovery now persists Graph's actual `parentReference.driveId` when it lists the connected account's `/me/drive`. An explicit selected drive that conflicts with the returned parent is rejected.

Older assessments can have valid frozen source item IDs, names and modified times but omit the drive ID. These scans need no rescan solely to recover routing metadata. The owner-scoped `POST /scans/{sid}/release/automatic/repair-source-identity` accepts an empty body and fresh Microsoft credentials through the existing authenticated connection. It neither approves remediation nor authorizes publishing.

Recovery is limited to a successfully completed, retained Discover job whose frozen SharePoint source selected the default drive with no explicit site, library or folder. Every missing-identity file must have a successful assessed record and score, matching item ID and modified time. Files with failed/unknown assessment remain blocked. Any already admitted Remediate stage blocks repair.

The server makes Graph GET requests through `$batch`: the default drive and each original item addressed through `/me/drive/items/{id}`. At most 500 files and 20 GET requests per batch are allowed; 147 files use eight batch requests. The whole provider verification has a 60-second budget; each request receives at most the remaining budget or 30 seconds. Timeout causes no partial repair. Every file must return its exact original ID/name, the resolved parent drive, unchanged modified time and matching algorithm-specific recorded checksum when present. Missing or unknown recorded checksum algorithms refuse verification. A provider failure or any mismatch causes no inventory writes. Provider responses establish current delegated access; unverified token claims do not grant permission.

Only after all checks pass does an atomic owner-scoped transaction acquire the same PostgreSQL `stage:{scan_id}:remediate` advisory transaction lock used by synchronous and queued remediation admission, before locking the owner scan row. It then compares the complete frozen provenance/assessment snapshot and fills NULL/empty inventory drive IDs. Existing identities, assessment results, source modification times, scope revisions and document bytes are unchanged. A concurrent source-context or remediation admission change refuses the transaction. No document content is downloaded or uploaded, and no job, blob, release-consent or automatic-release authorization is created.

Read-only readiness exposes `planning.source_identity_repair = {available, files, reason}`. This is candidacy, not a promise that current provider access is available. The frontend attempts one recovery per unchanged source context before refreshing readiness. Success returns `{status: "repaired" | "already_current", repaired_files}`; refusal returns an actionable structured reason. A disconnected Microsoft session must reconnect. A changed source requires normal discovery/assessment rather than rebinding an old result.

The affected production scan has not yet been repaired: its saved backend token is absent. After deployment, the current browser's authenticated Microsoft connection can perform the guarded recovery without a rescan, if all original source facts still match.
