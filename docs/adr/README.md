- [0045 — Controlled schema migration: what makes a deploy safe, and what does not](0045-controlled-schema-migration.md) — **Proposed** (2026-08-31) — design only, no pipeline change; the deployment half of the boot-lock work whose code half (replicas verify a version marker instead of replaying 139 DDL statements) ships separately. Its central claim is a NEGATIVE one, stated first because it is the conclusion most likely to be assumed: moving DDL to a separate deployment step is NOT sufficient — measured on the reproduction, three `queue_estimate` deadlocks still occurred against a single migrating process with replay already eliminated, and a separate step additionally makes the OLD code the first thing to meet the new schema, turning a loud boot failure into a silent estate-wide one. What actually makes it safe is that every migration is ADDITIVE (expand/contract, with contract deferred to a later deploy once no old-code replica remains) — the same property that makes deploy rollback safe without any schema rollback, which is why "write a down-migration" is the wrong instinct here. Adds a lock classification with only Class A permitted unattended, and records two findings from reading the current schema: all 16 index statements are non-concurrent, and they CANNOT be made `CONCURRENTLY` where they sit because `_apply_schema` wraps everything in one transaction; `DROP INDEX IF EXISTS idx_jobs_claim` is already non-additive. Also records why the version marker is an integer rather than a content checksum — a checksum has no ordering, so an old replica migrated BACKWARDS during a rolling deploy (measured: five migrations across five alternating boots, marker flapping). §6 adds the SECOND mixed-version window, which has nothing to do with the schema: `acp-app` gets real blue-green by ingress weight while `acp-worker` has NO INGRESS and therefore CUTS OVER unprotected at promotion (redeploy.sh:269-282 documents this deliberately), so a new app enqueues to an old worker — and the additive rule protects the SCHEMA contract, not the JOB PAYLOAD contract, which is enforced by nothing today. The known fix (queue partitioning) is named and scoped out, as redeploy.sh already does; what the ADR adds is that the two windows must not be reasoned about separately, and that the proposed deploy sequence orders only the schema half.
- [0046 — Blob intake at Assess: copy once, then never read the source again](0046-blob-intake-at-assess.md) — **Proposed** (2026-08-31) — design only, no code; ADR 0044 Phase 2's connector half, and the answer to "why does an expired token still break a queued Assess when ADR 0020 already shipped a source-bytes cache?" Because that cache is not an intake: ADR 0020 §Rollout 1 designed it around a Discover that opened every file, and stages 3+4 of the SAME ADR made Discover metadata-only — so the only surviving writer is the Assess path itself, AFTER its own `_download`. On a cold estate every first assessment is still a live connector fetch with the user's token; the cache helps a retry and a re-scan and has never helped the case that fails. It is also best-effort by construction (`cache_source_bytes` swallows everything — right for a cache, wrong for a durable copy), a miss silently reads CURRENT bytes (so file drift between Discover and Assess is invisible), and it has no document identity. Decision: copy at Assess start (not Discover — metadata-only is what makes Discovery fast, and Assess is where the four-format scope and the user's selection have already narrowed the set), make the copy AUTHORITATIVE with no connector fallback (a fallback is what makes the guarantee unstateable), and reuse ADR 0044's workspace layout and version identity rather than a fifth key shape beside `sources`/`remediated`/`thumbnails`/`workspace-content`. Answers the identity question 0044 left open — a connector document gets a workspace document row carrying `source_ref {source, external_id}`, and ADR 0003's `doc_id` contract is linked, never redefined. The checksum gate doubles as the drift detector. Retention ships with stage 1, not stage 3: the moment the first byte is copied is the moment the sweep needs to exist, or what has been built is an un-expiring PHI store. States the costs plainly — ACP now holds customer content (a customer-facing commitment change, not just an engineering one), and Blob becomes a hard dependency where the connector was a fallback.
- [0048 — Portable deployment packaging: one Helm release, per-cloud infrastructure adapters](0048-portable-deployment-packaging.md) — **Proposed** (2026-09-04) — PRD phase 0, contract only: no chart, no modules, no provisioning, and `deploy/public/` (Azure Container Apps) and `deploy/compose/` are untouched. Kubernetes + Helm is the portability layer and `platform` selects an INFRASTRUCTURE ADAPTER (managed data services, secret backend, ingress) rather than a different application package — a claim tested rather than asserted, by rendering the same workload for four platforms and requiring the application half of the Helm values to be byte-identical, with a companion test that the adapter half does differ so the identity cannot pass vacuously. Per-cloud native runtimes (ACA/ECS/Cloud Run) were rejected: three topologies to keep at parity instead of one, and ACA specifically has no PodDisruptionBudget, no NetworkPolicy and an 8Gi Consumption ceiling, so it cannot express three of the guarantees the regulated and HA profiles are defined by. Adds `packaging/schema/acp-deployment.schema.json` plus 19 semantic rules each of which has a test that MAKES IT FIRE, and a read-only `acpctl` (validate/plan/inventory/values) that enforces its own read-only promise by patching `open`. Two findings recorded rather than smoothed over: the connection-budget rule (derived from `store.db_max_conn` = ACP_WORKERS + _API_HEADROOM_CONN per replica, x MAX replicas — the 2026-08-30 `pool exhausted` incident) shows the PRD's own example replica ranges needing 518-604 connections against a Postgres confirmed live at 150, and the storage floor exempts Discover because ADR 0020 made it metadata-only — an exemption `ACP_DEFER_ANALYSIS_TO_ASSESS=0` invalidates and v1alpha1 does not model. `azure` is marked `planned`, not `supported`: `deploy/public/` deploys Container Apps, which is not the AKS adapter this contract describes.
- [0049 — Workspace RBAC: three authorization boundaries, and a rollout that can be reversed](0049-workspace-rbac-staged-rollout.md) — **Accepted** (2026-09-04) — the final slice of the Configurable ACP Roles PRD, and the ADR the first five should have had. Records the three boundaries kept deliberately separate (`core.is_admin`/`email_allowed` = may you use ACP at all; `acr_authz` = may you approve a conformance report, a decision with legal weight per ADR 0047; `workspace_rbac` = may you see this tab) and why no workspace capability may ever grant an ACR right — held by a test, not a convention, because an administrator editing a role must not be able to move that authority without anybody deciding to. The starting condition is that ACP had no workspace boundary at all: `ACP_OPEN_ACCESS` is on by default and `core.is_admin()` returns True for every authenticated user, so every "admin-only" route was reachable by anybody the allowlist admitted. Enforcement is ONE middleware over one route->capability table (not 236 decorators) specifically so "every route has a capability decision" is checkable rather than assumed — an unmapped route is allowed through, which is safe only because the completeness test makes one impossible to merge; that test is load-bearing. Slice 6 replaces the single `ACP_WORKSPACE_RBAC_ENABLED` boolean with a four-rung ladder (off -> observe -> navigation -> enforce): `observe` resolves roles and records what enforcement WOULD refuse at zero user impact, because a capability map that is subtly wrong is invisible in tests (tests assert the mapping we intended; only real traffic exercises the one we wrote), and `navigation` removes the click-a-tab-get-403s failure on its own. The old variable still means enforce — a release that quietly stopped honouring it would turn a security control OFF in a workspace that believed it was enforcing. An unreadable mode never resolves to enforce (locking a workspace out on a typo) but is reported as a preflight blocker, because running unenforced while believing otherwise is the state nobody notices. Also records the one deliberate reversal of fail-closed — an unassigned signed-in user gets the default Platform User role, since `email_allowed` already admitted them, while suspended and unresolvable-role still get nothing ("nobody has decided yet" and "a decision was recorded and cannot be read" are different facts) — and why observations and real refusals are separate audit actions with separate coalescing windows: sharing one would let a suppressed observation swallow the first genuine 403 after an operator advances, which is the most important row in the whole rollout. PRD §15 steps 4-5 are explicitly NOT done, since both depend on observation data that does not exist yet.
