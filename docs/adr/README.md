- [0043 — SSE resume for scan progress: `Last-Event-ID` rejected, history-on-reconnect adopted](0043-sse-resume-history-on-reconnect.md) — **Proposed** (2026-08-29) — design only, no code; the ADR 0042 PR 5 that 0042 deferred to its own decision, and the answer is DON'T: these streams are snapshot-REPLACE (every frame is full current state, per liveJobStateGuard.js), so replaying frames to a client one tick from the next snapshot delivers superseded copies — `Last-Event-ID` solves a delta-stream problem this app does not have; what a disconnect actually costs is NARRATIVE (a `retrying` that came and went), which `GET /scans/{sid}/history?after_seq=` already returns from PR 3. Verified against the code: nothing emits `id:`, `parseSSEFrames` discards `id:` lines, the discover stream is `fetch`+ReadableStream (not EventSource — auth headers) so browser resume does not apply, `pollScanJob` closes on error so native auto-reconnect never fires, and `GET /scans/{sid}/events` has NO consumer at all (the running screen polls `/live` at 2s) — which also corrects 0042's endpoint table. Adopted instead: one `GET` in the existing onDone handler, zero stream-contract change. Names four conditions that would reopen it, and flags the orphan endpoint as a separate call.
